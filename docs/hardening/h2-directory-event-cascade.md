## 1. Executive Summary & Verification Matrix

Hardening Task H2 investigates, characterizes, and resolves filesystem event cascades generated by large directory tree deletions, moves, and renames. Under Windows filesystem event notification mechanisms (`ReadDirectoryChangesW`), modifying a large folder tree (e.g. 5,000 to 10,000 files) emits hundreds to thousands of granular child file events. Without directory-level event coalescing and batch database processing, this produces SQLite transaction contention, queue flooding, and delayed legitimate indexing.

## 2. Characterization & Vulnerability Analysis

### A. Existing Un-Remediated Behavior
1. **Directory Event Dropping**: `FolderWatchHandler` previously contained `if event.is_directory: return`, completely ignoring `DirMovedEvent` and `DirDeletedEvent`.
2. **Move/Rename Data Loss**: Renaming a folder tree on Windows resulted in all child files in SQLite permanently pointing to obsolete, non-existent disk paths because Windows watchdog emits `DirMovedEvent` and synthetic child moved events that were dropped.
3. **Transaction Explosion**: Individual child `FileDeletedEvent` notifications were processed in separate `with db.session()` context blocks, triggering up to 1,000 individual transactions per second, contending SQLite write locks and creating audit log bloat.

### B. Event Boundary Distinctions
- **A. Raw OS / Watchdog Events**: 1,013 events emitted per 1,000-file directory deletion (directory modified + individual child file deletions + directory deletion).
- **B. Normalized Logical Events**: Coalesced inside sliding window (0.3–0.5s) where child events under a deleted/moved directory are subsumed into a single logical directory event or batched list.
- **C. Queued Job Events**: Obsolete child indexing jobs for deleted files are canceled in bulk via `UPDATE indexing_jobs SET status = 'CANCELLED'`.
- **D. Database State Operations**: Single atomic query `mark_directory_missing` and `rename_directory_path` execute within one SQLite transaction per flush.
- **E. Final State Convergence**: 100% agreement between real filesystem and SQLite database state.

## 3. Implementation Details

### A. Repository Subtree Layer (`backend/app/db/repository.py`)
1. `mark_directory_missing(folder_id, dir_path)`:
   - Sets `index_status = 'MISSING'` and `last_seen_at = now` for all files matching `folder_id` and `path LIKE 'dir_prefix/%'` in a single atomic SQL statement.
   - Cancels all pending/processing indexing jobs for those files in the same transaction.
2. `rename_directory_path(folder_id, old_dir_path, new_dir_path, root_folder_path)`:
   - Queries all files matching `old_dir_path` prefix.
   - Replaces the path prefix, updates `relative_path` relative to `root_folder_path`, and enqueues priority-2 `HASH_VERIFICATION` jobs.

### B. Watcher & Debouncer Layer (`backend/app/engine/watcher.py`)
1. `is_subpath(child_path, parent_path)`:
   - Canonicalizes paths and ensures Windows case-insensitivity and separator normalization (`replace('\\', '/')`).
2. `DebouncedEventManager`:
   - Prunes pending child events when a directory event (`DIR_DELETE` / `DIR_MOVE`) arrives.
   - Drops redundant child file events if a parent directory event is already pending.
   - Supports `on_flush_batch` to dispatch entire event queues into a single SQLite transaction.
3. `WatcherService`:
   - Implements `_handle_flushed_batch(events)` which executes all audit logging and subtree updates in a single `db.session()` transaction.
   - Calls `self.debouncer.flush()` on `stop()` to guarantee zero dropped events during shutdown.

## 5. Correctness & Security Invariants

1. **Path Traversal & Security**: Subtree operations validate registered root containment and enforce `is_subpath` semantics.
2. **Case Insensitivity**: Windows case variations (e.g. `C:\dev\PROJ` vs `c:\dev\proj`) resolve identically.
3. **Delete/Recreate Safety**: `mark_directory_missing` checks `if not os.path.exists(path)` before marking missing to avoid deleting newly recreated files.
4. **Nested Root Isolation**: Queries require `folder_id = ?`, preventing parent directory operations from affecting independently registered nested child folders.
5. **Phase Scope**: Hardening tasks H3, H4, and Phase 4 remain strictly **NOT STARTED / NOT AUTHORIZED**.
